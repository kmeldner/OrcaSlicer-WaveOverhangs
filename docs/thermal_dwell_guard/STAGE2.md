# Thermal Dwell Guard — Stage 2 Specification (Rev B): Standalone Module + Chute-Based Flush Injection

**Status:** ready to implement (Stage 1 implemented, testing in progress)
**Placement:** `docs/thermal_dwell_guard/STAGE2.md` — REPLACES any earlier Stage 2 spec (Rev A).
**Rev B changes vs Rev A:** (1) the scope option is REMOVED entirely — the guard always
monitors the whole print and no longer depends on wave-overhang markers in any way;
(2) the flush no longer purges on the bed — it travels to the printer's designated flush
position (X1C chute + wiper) and replicates the machine's own purge/wipe motion subset.
**Relationship to SPEC.md / STAGE1.md:** this file governs Stage 2. Update SPEC.md,
STAGE1.md (scope references), and CLAUDE.md in the same commit.

---

## Part A — Full decoupling from wave overhangs (do first, small)

**Decision:** the Thermal Dwell Guard is a standalone module. It catches slow extrusion
from ANY cause — slow outer/inner wall, slow infill, overhang slowdown, bridges, wave
overhangs — purely from the flow rate of each move. It must not read or depend on wave
markers at all.

Tasks:

1. **Remove** `thermal_dwell_scope` and the `ThermalDwellScope` enum completely:
   PrintConfig declaration, config-class member, enum registration, UI item, serialization.
   (Early-dev fork: no migration shim needed; a stale key in old profiles may be ignored.)
2. **Accumulator:** drop the "in scope" condition — rows 1/2 of the STAGE1 §4 table merge
   into one: slow extrusion ALWAYS accumulates. Remove `in_wave_region` tracking and the
   wave-marker parsing from `ThermalDwellGuard`.
3. **Checker script:** remove the wave-region containment check; everything else stays.
4. **UI:** "Thermal dwell guard" is its own group in Print Settings, a peer of (not
   nested under) the wave overhangs group.
5. **Wording/docs:** tooltips and SPEC/CLAUDE.md present the guard as standalone; wave
   overhangs is one example trigger. Note the module now has zero dependency on this
   fork's wave code and is portable to stock OrcaSlicer.

## Part B — Forced flush injection at the machine flush position

### 1. Objective and hard rules

At every Stage-1 flush point, inject a real flush: retract → z-hop → travel to the
machine's flush position (X1C chute) → purge → wipe on the machine wiper → return →
restore state → resume. ForcedOnly semantics; `thermal_dwell_schedule_mode` and
`thermal_dwell_lookahead` are STILL NOT read (Stage 3).

**Invariant 1 — pure insertion.** The guard only INSERTS lines; it never modifies,
reorders, or deletes an original line. Guard-ON output == guard-OFF output + inserted
blocks. Mechanically checkable.

**Invariant 2 — state neutrality.** After the last inserted line of a block, the state
seen by downstream original lines (XY, Z, logical E, retract state, modal feedrate, fan,
temperatures, E mode, tool) is IDENTICAL to the state at the anchor.

**Invariant 3 — no machine-state side effects.** The flush changes NO temperatures, NO
fan state, issues NO AMS commands (M620/M621), NO filament cut, NO pauses requiring user
interaction. It is motion + extrusion only, at current print temperature.

With `thermal_dwell_guard_enable = false`: byte-identical output.

### 2. Why not splice the machine's change-filament G-code

The X1C change-filament sequence performs a FULL material change: AMS unload/load,
filament cut at the cutter, temperature ramps, long purge — minutes of time and state
changes that are wrong and destructive for a flush. The guard instead replicates the
RELEVANT MOTION SUBSET of the machine's own routine: travel to chute, purge, wiper drag.
Same place, same wipe action, none of the side effects — and the purge is generated by
the guard so E-accounting stays provably correct.

### 3. X1C flush-position and wiper extraction (development-time, not runtime)

Do NOT parse the user's machine G-code at slice time to discover the chute (arbitrary
templates have no reliable anchor; heuristics break silently). Instead:

- In the fork's bundled Bambu profiles (`resources/profiles/BBL/machine/...`), locate the
  X1C machine G-code — BOTH the start G-code and the change-filament G-code. Bambu
  comments its sections; find the nozzle purge/wipe portion (prefer the change-filament
  one — it is the mid-print flush Bambu ships).
- Extract: chute purge XY, wiper sweep coordinates/pattern, approach order, and any Y
  overtravel used (the chute sits beyond the bed's Y edge at gantry level; the bed drops
  away below it, which is why it is reachable at any print height — Bambu itself flushes
  there mid-print).
- **Whitelist for replication:** motion only (G0/G1 XY moves, G4 dwells if present).
  EXCLUDE: M620/M621 and all AMS commands, the filament-cut move, temperature commands,
  fan commands, M400-style sync unless required, any G92 (the guard does its own).
- Bake results as: the new DEFAULT of `thermal_dwell_flush_position` (chute XY) and a
  built-in X1C wiper pattern used when `thermal_dwell_wipe = true`.
- **Cite the exact profile file and lines in the exploration report. Do not invent
  coordinates.**

v1 covers the X1C only. Other printers later (likely via a per-machine flush template —
out of scope now). The generic "flush XY inside printed-bbox" warning from Rev A stays,
for users who point the position somewhere unwise.

Config semantics updates (same keys, new meaning — update tooltips):
- `thermal_dwell_flush_position`: default = X1C chute XY (extracted). Tooltip: machine
  flush/wipe position; default is the Bambu X1C chute.
- `thermal_dwell_wipe`: wipe on the machine wiper at the flush position (X1C pattern
  built in), default true.
- `thermal_dwell_flush_z_lift` unchanged (clear the print top before XY travel).

### 4. State snapshot at the anchor

From GCodeProcessor state at the anchor line: X, Y, Z; logical E and E mode (M82/M83);
retract state; modal feedrate F; active tool. Fan and temperatures untouched.

### 5. The flush sequence (exact order)

Let `A` = filament cross-section area, `E_p = thermal_dwell_purge_volume / A`,
`F_p = thermal_dwell_purge_flow / A * 60` (mm/min), `r` = active `retract_length` with
`retract_speed`/`deretract_speed`, travels at `travel_speed`, lift =
`thermal_dwell_flush_z_lift`.

1. **Retract `r`** — only if not already retracted at the anchor.
2. **Z-hop** to `Z_anchor + lift`.
3. **Travel** to the flush position (chute XY), at `travel_speed`. If the extracted Bambu
   routine uses a specific approach order (e.g. Y first), replicate it.
4. **Unretract** (filament must be primed to purge).
5. **Purge:** extrude `E_p` total at `F_p` (E-only moves; chunking allowed).
6. **Wipe** (if enabled): the extracted X1C wiper drag pattern, motion-only.
7. **Retract `r`.**
8. **Travel back** to (X,Y)_anchor.
9. **Z restore** to `Z_anchor`.
10. **Unretract only to match the anchor's retract state.**
11. **E bookkeeping:** absolute-E mode → emit `G92 E<E_anchor_logical>` (MANDATORY —
    omitting it wrecks every downstream absolute E target). Relative mode → no fixup;
    retract balance must net to the anchor state.
12. **Restore modal feedrate:** `G1 F<F_anchor>`.
13. Accumulator resets at the flush (Stage 1 semantics).

Every inserted move carries an explicit F. No inserted line may rely on ambient modal
state, and none may change state that outlives the block (Invariant 2).

### 6. Exclusion zones

Never anchor a flush inside: toolchange / wipe-tower blocks, filament-change sequences,
or custom-G-code blocks (layer-change custom gcode, pause blocks). Confirm this fork's
markers (upstream style: `; CP TOOLCHANGE START/END`). If the crossing lands inside a
zone, DEFER the anchor to the first safe line after it (accumulator keeps running; the
flush fires late rather than corrupting a block). v1 targets single-extruder,
single-material printing; multi-material is untested — document that.

### 7. Marker grammar (extends Stage 1; keep stable)

```
;THERMAL_DWELL_FLUSH_POINT id=<n> acc=<f>s layer=<n> z=<f>     <- kept from Stage 1
;THERMAL_DWELL_FLUSH_START id=<n>
  ... inserted sequence ...
;THERMAL_DWELL_FLUSH_END id=<n>
```

SUMMARY gains totals: `;THERMAL_DWELL_SUMMARY count=<n> total_purge_mm3=<f>
est_added_time_s=<f>`. CONFIG echo now includes the Group-3 values and drops scope.

### 8. Safety notes / accepted v1 limitations

- M73 progress estimates exclude flush time (computed pre-injection). Accepted; seconds
  per flush.
- Live slice preview does not show injected motion (accepted decision). Verification
  uses re-import of the exported .gcode into Orca's viewer.
- Resume blemish: slight ooze after purge+return can leave a zit at the resume point.
  v1 uses standard retraction; an extra-restart-retract knob is a possible later add.
- Runaway configs: WARN if flush count exceeds ~100.
- First layer is not excluded (slow first layers heat-soak too).

### 9. Verification

**a) Checker script extensions** (`check_thermal_dwell.py`):
- Pure-insertion check: guard-ON file == guard-OFF file + inserted blocks only (plus
  CONFIG/SUMMARY comments).
- Per block: markers paired, ids consecutive; travel targets the configured flush
  position; wipe pattern present when enabled; final XY/Z equal the anchor's;
  retract/unretract balance to the anchor state; purge E total = `purge_volume/A` within
  1%; explicit F on every inserted move; absolute-E files contain the `G92 E<anchor>`;
  final modal-F restore matches the anchor.
- Invariant-3 scan: no M104/M109/M140/M106/M620/M621/cut moves inside blocks.
- E-mode (M82/M83) detected from the file. Stage-1 checks still pass (minus the removed
  region check).

**b) Unit tests** (if harness usable): sequence generator vs synthetic anchor states —
absolute/relative E, retracted/unretracted anchors, wipe on/off; assert exact line
sequence and state neutrality.

**c) Visual check:** re-open the exported .gcode in Orca's viewer; scrub a flush;
confirm travel → chute → return with no motion through the part at print Z, and Y
overtravel to the chute present.

**d) First live print protocol** (only after a–c pass): small test model, `max_time`
lowered (e.g. 60 s) to force 2–3 flushes, PLA, watch the first flush end-to-end with a
hand near pause. Confirm: purge into chute, wiper drag, clean return, no post-resume
extrusion anomaly (the G92 check on metal).

1. Slicer build succeeds (slicer build only).
2. Guard OFF: byte-identical G-code (diff).
3. Guard ON, zero crossings (fast print): output identical except CONFIG/SUMMARY.
4. Guard ON, slow test model with lowered `max_time`: every FLUSH_POINT followed by a
